# Does the memory service actually help? — measured, 2026-09-03

Generated by `benchmarks/session_analytics.py` (`make analytics`). Raw output:
`benchmarks/results/session-analytics-20260903.json`.

Every quality number this repo had before today came from a replay harness: a
query set, a gold answer, an MRR. That measures the ranker. It does not measure
whether what the ranker surfaced was of any use to the agent that received it.
This report measures the second thing.

## 2. Injection usefulness — last 5 weeks

202 hook injections carrying 657 memories (648 scorable).

Method: for each injected memory, take the distinctive tokens of its preview
(≥8 chars, not a stopword, not a bare number) and ask whether ≥2 of them reappear
in assistant text written *after* the injection. Two controls bracket the answer
rather than pin it:

- **ordered** — subtract only what the agent had already seen when the injection
  landed. A file it read afterwards may have been read *because* of the memory,
  so subtracting that would erase real credit. Upper bound.
- **strict** — subtract everything the agent saw from any other source at any
  point in the session. Erases genuine credit whenever a memory and a later file
  share vocabulary. Lower bound.

**Used rate: 15.3% (ordered) … 2.0% (strict).**

| type | n | used (ordered) | used (strict) |
|---|---|---|---|
| learning | 165 | 18.8% | 4.8% |
| reference | 110 | **3.6%** | 0.0% |
| error | 99 | 16.2% | 2.0% |
| pattern | 89 | 13.5% | 0.0% |
| decision | 66 | **28.8%** | 1.5% |
| note | 62 | 11.3% | 1.6% |
| observation | 52 | 15.4% | 0.0% |
| todo | 5 | 40.0% | 20.0% |

At best roughly one injected memory in six leaves a visible trace. The spread by
type is the actionable part: `decision` is used eight times more often than
`reference`, yet `reference` occupies 110 of the 657 injected slots. The hook
injects five lines per session; giving even one of those slots back to `decision`
at `reference`'s expense is a free change.

## 3. Score calibration — is `--min-score 0.5` in the right place?

| score bucket | n | used (ordered) | used (strict) | mean reused tokens |
|---|---|---|---|---|
| ≥0.70 | 42 | **0.0%** | 0.0% | 0.10 |
| ≥0.65 | 25 | 12.0% | 0.0% | 0.64 |
| ≥0.60 | 63 | **22.2%** | 0.0% | 0.83 |
| ≥0.55 | 204 | 19.1% | 2.9% | 0.75 |
| ≥0.50 | 314 | 13.7% | 2.2% | 0.60 |

**Retrieval score does not predict usefulness, and at the top it inverts.** The
best-scoring bucket is the least used, by a wide margin and with n=42.

Read this carefully, because there are two readings and only one is right.

A memory scoring ≥0.70 is by construction very close to the prompt. Its
vocabulary is therefore mostly already *in* the prompt, so the control subtracts
it and there is nothing left to detect. Part of the 0.0% is that measurement
artifact. But the artifact and the finding are the same phenomenon seen from two
sides: **a memory that closely restates the prompt tells the agent nothing it did
not just read.** High similarity is not high informativeness. This is the
standard argument for a diversity term (MMR, or the CSLS hubness correction the
ranker already applies at fusion time) and the data says it applies to the
injection decision too, not just to ranking.

What it does *not* say is that the ranker is broken. `weighted_best` scores 0.970
MRR on the production corpus (`benchmarks/results/README.md`). It finds the right
thing. The question this table raises is whether "the closest thing" is what the
injection slot should be spent on.

Practical consequence: raising `--min-score` would make things worse, not better.
The hook's own comment already notes ~96% of prompts clear 0.5, i.e. the
threshold is near-inert. These numbers say leave it inert — the useful band is
0.55–0.65, and a floor cannot select a band.

## 4. Write/read coverage — full history

2 145 of 5 869 live memories (36.5%) have never been recalled.

**That number is an undercount, and the contamination is measurable.** Three days
each bumped ≥100 memories at once — 2026-06-23 (1 874 memories), 2026-08-30
(147), 2026-08-25 (131), 2 152 in total. A sweep with recall tracking on is not
reading. Every memory it touched now looks recalled. Of the 2 458 memories older
than 90 days, exactly **one** has `recall_count = 0`, which is not a plausible
organic outcome. `benchmarks/session_analytics.py` now detects and prints this
automatically so it does not have to be rediscovered.

Age-stratified, which is the only honest way to read it:

| age | n | never recalled |
|---|---|---|
| 0–7d | 338 | 78.1% |
| 7–30d | 1 446 | 77.6% |
| 30–90d | 1 627 | 46.6% |
| 90d+ | 2 458 | 0.0% ← contaminated, ignore |

By type, `error` (47.8%) and `observation` (47.9%) are written most and read
least; `decision` averages 40.4 recalls each, an order of magnitude above
everything else. Same signal as measure 2, from an independent direction:
**decisions earn their storage, observations largely do not.**

## What to do about it

Ranked by evidence strength, not by effort.

1. **Attack the 13.1% zero-result rate.** Largest measured failure, full seven
   months of data behind it, and completely unaddressed by the current
   benchmarks. Start by logging the queries that return nothing — the schema
   already has a `query` column on `operation_events`.
2. **Rebalance what the injection slots hold.** `decision` is used 8× more than
   `reference` and gets fewer slots. This is a scoring-weight change, not new
   machinery.
3. **Stop treating score as a usefulness proxy.** The ≥0.70 band is the least
   useful one. A diversity/novelty term on the injection decision is indicated;
   raising the score floor is contraindicated.
4. **Do not trust `recall_count` before 2026-07** for any lifecycle decision —
   demotion, forgetting, index tiering all read it, and for the pre-June corpus
   it reflects one sweep rather than seven months of use.

## Limits of this analysis

- Reuse is token overlap, not comprehension. A memory that correctly told the
  agent *not* to do something leaves no trace and is scored zero. This class of
  usefulness is systematically undercounted and the size of the undercount is
  unknown.
- The hook injects `--depth summary`, so the transcript holds a ~200-char preview,
  not the full memory. Mean distinctive tokens per memory is ~5, so single-token
  noise moves the metric easily.
- The hook fires once per session, so n ≈ one injection per session. Enough to
  calibrate a global threshold; too thin to slice per project.
- `memories.recall_count` counts CLI and skill recalls too, so it is not a measure
  of hook effectiveness on its own — which is why measures 2 and 4 are kept apart.
