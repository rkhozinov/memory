2. Injection usefulness — last 5 weeks

202 hook injections carrying 657 memories (648 scorable).

Method: for each injected memory, take the distinctive tokens of its preview (≥8 chars, not a stopword, not a bare number) and ask whether ≥2 of them reappear in assistant text written after the injection. Two controls bracket the answer rather than pin it:

  • ordered — subtract only what the agent had already seen when the injection landed. A file it read afterwards may have been read because of the memory, so subtracting that would erase real credit. Upper bound.
  • strict — subtract everything the agent saw from any other source at any point in the session. Erases genuine credit whenever a memory and a later file share vocabulary. Lower bound.

Used rate: 15.3% (ordered) … 2.0% (strict).

Retrieval score does not predict usefulness, and at the top it inverts. The best-scoring bucket is the least used, by a wide margin and with n=42.

Read this carefully, because there are two readings and only one is right.

A memory scoring ≥0.70 is by construction very close to the prompt. Its vocabulary is therefore mostly already in the prompt, so the control subtracts it and there is nothing left to detect. Part of the 0.0% is that measurement artifact. But the artifact and the finding are the same phenomenon seen from two sides: a memory that closely restates the prompt tells the agent nothing it did not just read. High similarity is not high informativeness. This is the standard argument for a diversity term (MMR, or the CSLS hubness correction the ranker already applies at fusion time) and the data says it applies to the injection decision too, not just to ranking.

What it does not say is that the ranker is broken. weighted_best scores 0.970 MRR on the production corpus (benchmarks/results/README.md). It finds the right thing. The question this table raises is whether "the closest thing" is what the injection slot should be spent on.

Correction, added after probe P5. The paragraph above is about score bands across injections. It does not license the conclusion that a novelty term would help within one injection — and P5 measured that directly and refuted it. MMR selection over a reconstructed 20-candidate pool is monotonically worse than plain top-5-by-score (22.3% → 15.1% as diversity weight rises), even as redundancy falls exactly as designed. Within a pool, score still predicts usefulness better than novelty does. See docs/research/consolidation-redesign.md §P5.

Practical consequence: raising --min-score would make things worse, not better. The hook's own comment already notes ~96% of prompts clear 0.5, i.e. the threshold is near-inert. These numbers say leave it inert — the useful band is 0.55–0.65, and a floor cannot select a band.

4. Write/read coverage — full history

2 145 of 5 869 live memories (36.5%) have never been recalled.

That number is an undercount, and the contamination is measurable. Three days each bumped ≥100 memories at once — 2026-06-23 (1 874 memories), 2026-08-30 (147), 2026-08-25 (131), 2 152 in total. A sweep with recall tracking on is not reading. Every memory it touched now looks recalled. Of the 2 458 memories older than 90 days, exactly one has recall_count = 0, which is not a plausible organic outcome. benchmarks/session_analytics.py now detects and prints this automatically so it does not have to be rediscovered.

What to do about it

Ranked by evidence strength, not by effort.

  1. Stop the slash-command leak. 48 /command queries reached search since May. hooks/memory-topic-recall.sh skips slash commands, so these come from another caller. Small, certain, and the only actionable part of what looked like a 13.1% failure rate.
  2. Rebalance what the injection slots hold. decision is used 8× more than reference and gets fewer slots. This is a scoring-weight change, not new machinery.
  3. Stop treating score as a usefulness proxy. The ≥0.70 band is the least useful one. A diversity/novelty term on the injection decision is indicated; raising the score floor is contraindicated.
  4. Do not trust recall_count before 2026-07 for any lifecycle decision — demotion, forgetting, index tiering all read it, and for the pre-June corpus it reflects one sweep rather than seven months of use.

Limits of this analysis

  • Reuse is token overlap, not comprehension. A memory that correctly told the agent not to do something leaves no trace and is scored zero. This class of usefulness is systematically undercounted and the size of the undercount is unknown.
  • The hook injects --depth summary, so the transcript holds a ~200-char preview, not the full memory. Mean distinctive tokens per memory is ~5, so single-token noise moves the metric easily.
  • The hook fires once per session, so n ≈ one injection per session. Enough to calibrate a global threshold; too thin to slice per project.
  • memories.recall_count counts CLI and skill recalls too, so it is not a measure of hook effectiveness on its own — which is why measures 2 and 4 are kept apart.
  • Aggregate rates over this DB mix real usage with eval-harness traffic. 62% of zero-result queries with text are verbatim repeats; the same caution applies to every count in measure 1. Split by mode and by repetition before drawing a conclusion from any of them.
